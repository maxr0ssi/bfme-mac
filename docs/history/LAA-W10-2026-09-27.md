# 4 GB address space (LARGEADDRESSAWARE) on the w10 engine

Question (2026-09-27): the games run with the LAA flag cleared (`tools/pe_laa.py --off` in
`scripts/install.sh`) because "LAA crashes under Wine" (PLAYING.md, patches/README.md, LOAD-TIME.md,
harness rule). The art mod wants the extra 2 GB for textures. Does LAA crash on **w10**?

## 1. Every recorded LAA crash was on Wine 11.0, and was the WoW64 bug

The claim dates from 2026-09-22 (commit 631b41c), when BFME2 still ran on Gcenx Wine 11.0 and the
10.0→11.0 WoW64 regression (patches/WINE-BUG-REPORT.md) was not yet understood. Each game-folder
minidump names its engine through the timestamp of the loaded 32-bit `ntdll.dll`
(`0x69e0eaba` = engines/stable 11.0, `0x6aa38190` = staging 11.17, `0x691dc439` = cx,
`0x69d97c0e` = w10):

| when (09-22) | game | engine | fault | what it is |
|---|---|---|---|---|
| 11:28 | BFME2 | — | `game.dat.preLAA.bak` written: LAA set on | the experiment |
| 11:30 (run 11:29:07, ~60 s: the harness's "crashes ~60 s in") | BFME2 | 11.0 | `0x7BF2123D` read `0x4DC9`, render thread | `syscall_32to64` run as 32-bit code: the Wine 11 bug |

No w10 run with the flag on exists in `logs/` or the dumps. LAA was never tried on w10.

## 2. What w10 does with the flag (source and probe)

Wine 10.0 (`wine/src-d3dx10`): `virtual_set_large_address_space()` sets the WoW64 user limit to
4 GB − 1 when the exe has the flag; `wow64` and `win32u` derive their `zero_bits` from
`HighestUserAddress`; the 32→64 thunks (opengl32 `unix_wgl.c`, the generated GL thunks, winemac) all
widen pointers with `ULongToPtr` (zero-extension); our `wined3d.so` passes the source address as a
zero-extended `UINT64`. No sign-extension or 2 GB assumption was found on the paths the game uses.

`tools/laaprobe.c` (LAA-flagged test exe) run with `scripts/laa-probe.sh` on w10, 2026-09-27,
throwaway prefix, no game:

```
exe LAA flag: on
MaximumApplicationAddress FFFEFFFF, TotalVirtual 4095 MB, AvailVirtual 4055 MB
space: reserved 4044 MB in 707 blocks, 2032 MB above 2 GB, highest end 0xffff0000   (every block committed, written, read)
topdown: MEM_TOP_DOWN 1 MB at FFF00000                                               (written, read)
0 failure(s)
```

So the engine and Rosetta give a 32-bit process the full 4 GB and 32-bit code reads and writes
memory up to `0xFFFF0000`.

## 3. The game's side

RotWK 2.02 ships `lotrbfme2ep1.exe` and `game.dat` with the flag on: the patch team runs the game
above 2 GB on Windows, so the game's own code (memory pools, pointer compares) is exercised there.
BFME2 1.06 ships without it. The game patch checks the exe's base and timestamp, not the flag.

## 4. Probe results on w10 (2026-09-27)

Every test passes, with nothing crashing:
- `scripts/laa-probe.sh`: all tests, then all again with the low 2 GB reserved **and the process
  heap's low free space used up**. That second step is needed: without it, d3d9's and dsound's lock
  memory came from heap segments reserved before the fill, below 2 GB.
- High-address results: the heap at 0x808…, a thread stack at 0x809FFE03 (SEH, RtlUnwind,
  vectored handlers, 20000 window callbacks), d3d9 managed, system-memory and dynamic textures and
  vertex buffers locked at 0x800…, all drawn and checked pixel by pixel. The game's 13 DLLs load,
  D3DX decodes into a managed texture, and a dsound buffer locks at 0x80004A64.
- `--fill-low --mb 1500 d3d9`: 1500 MB of managed textures, all locked above 2 GB, all drawn
  correctly. The bulk draw now samples the 512-pixel textures 1:1; the first run's 309 "wrong
  draws" were the probe comparing a minified draw against the full-size pattern.

## 4b. Our game patch above 2 GB (2026-09-27 audit)

`gamepatch/src` (every `.S` and `.c` file, and the thread pool it uses) is clean. The signed
jumps and 0x80000000 compares test float bits, not addresses. Pointers only ever convert to
`uint32_t`/`uintptr_t`. The "is it mapped" and "inside a module" checks ask Windows. Hashes and
pointer differences are unsigned. The game code at the hook sites compares counters, not
addresses. `eipsample.c` and `fpsample.c` do unsigned DWORD maths. The game's own unhooked code is
not audited; RotWK runs with the flag on Windows.

## 5. The owner's in-game test

RotWK's `game.dat` and `lotrbfme2ep1.exe` have the flag **on** since 2026-09-27
(`tools/pe_laa.py --on`; `game.dat` is now byte-identical to the shipped `game.dat.preLAAoff.bak`;
the flag-off files are kept as `*.preLAAon.bak`). BFME2 stays off (retail ships it off). Play a
long skirmish with the art mod, with `scripts/memwatch.sh` running, then check `logs/` and any new
`DUMP_*.dmp` (`tools/parse_minidump.py`). Memory above 2 GB is only used once the first 2 GB is
full, so a short game proves little. Revert: `tools/pe_laa.py --off` on both files.
`scripts/install.sh` now sets the flag the way each game ships it: on for RotWK, off for BFME2.
The harness rule against the flag is gone, and PLAYING.md, LOAD-TIME.md, REFERENCE.md and
patches/README.md are corrected.

**Quick test, one session:** `GAMEPATCH_HIGHMEM=1 scripts/play-rotwk.sh` (gamepatch installed;
or `highmem=1` in the game folder's `gamepatch.ini`) reserves the free space below 2 GB at start-up
except `highmem_slack` (256 MB), so the game's memory is above `0x80000000` within minutes: check
for the `highmem: reserved … MB` line in `logs/gamepatch.log`, play a normal skirmish and look for
crashes, missing textures or sound, or new `DUMP_*.dmp`; off again by starting without the variable
(or `highmem=0`). Checked without the game by `gamepatch/tests/t_highmem.c`.
