# assets: building recipes

New art for BFME2 / RotWK, built from each player's own install by `sagekit` (the engine, in
`sagekit/`). This folder holds **only recipes**: Python classes and notes. Never EA files, never
built output (that goes to `build/assets/`, which git ignores).

The map of the engine (steps, modules, standards, where each faction stands) is
[docs/ART.md](../docs/ART.md); what comes next is [docs/FACTIONS-PLAN.md](../docs/FACTIONS-PLAN.md).

## Rules

1. **One palette per faction.** A faction's `style.py` defines one `Style`: palette, materials,
   shape vocabulary, paint stack. Every building imports it; nobody picks their own gold.
2. **One damage style per faction.** Damage, rubble and construction states are generated by the
   faction's damage recipe, not hand-made per building (see *Lifecycle*).
3. **The whole faction.** A faction is done when `inventory` shows every part of every building
   built, add-ons and upgrades included.
4. **Strict taxonomy.** Fixed folder layout, fixed state names, automatic texture names;
   `python3 -m sagekit validate` fails anything else.
5. **Memory budget.** The game is a 32-bit program with 4 GB of address space (RotWK's 4 GB flag,
   [docs/MEMORY-4GB.md](../docs/MEMORY-4GB.md)); every texture byte takes 1.03 bytes of it while
   loaded, and a TGA normal map takes 5.33 bytes a pixel (32-bit with mips,
   [docs/MEMORY-2GB.md](../docs/MEMORY-2GB.md)). `Tier.HERO` (4096 texture) only for the building a
   faction is recognised by; everything else `Tier.STANDARD` (2048). `validate` refuses a faction
   over its `Style.budget_mb` (512 MB).
6. **Nothing installs without review.** A build ends in renders; installing is a separate command.

## Layout

```
assets/<faction>/                    men, elves, dwarves, isengard, mordor, goblins, angmar
    style.py                         class <Faction>Style(Style)
    atlas.py                         the faction's shared source sheet(s): regions + mask hints
    shapes.py                        the faction's shape vocabulary (Blender side)
    <building>/                      snake_case
        building.py                  class <Name>(Building): source, target, tier, design()
        README.md                    short notes, see *Building README* below
```

## Commands

```bash
python3 -m sagekit list
python3 -m sagekit validate
python3 -m sagekit inventory dwarves/fortress
python3 -m sagekit build dwarves/fortress
```

`build` runs `extract → geometry → bake → paint → export → night → fixup → derive → lifecycle → ship →
shared → ini → cache → checks → render`;
`--from STEP --to STEP` runs a slice (iterating on a design: `--from geometry --to render`). The
result is in `build/assets/<faction>/<building>/`: `out/` holds exactly what ships (archive paths),
`renders/compare_*.png` the before/after, `work/logs/` every step's log.

After visual review, `python3 -m sagekit install <faction> --check` stages a pack and verifies
cache changes without installing. Omit `--check` to install; `--revert` restores the last
installation's scoped backups. Installation preserves other factions and units in the current
cache. Revert refuses if later work changed a touched file, rather than resetting the shared
cache to its original state.

## Adding a building

1. `python3 -m sagekit inventory dwarves/<name>` on a stub to see its parts and states.
2. Write `building.py`: `source` (the healthy model), `target` (the mesh to redesign), `tier`,
   measurements taken from the original, and `design(kit)` built from the faction's shapes.
   Buildings of the faction share the atlas, so new faces are mapped onto real painted stone.
   A recipe that rebuilds a volume of EA's instead of dressing it names EA's faces to remove,
   `clear = [Box(...), Piece(...), Where(...)]` (`sagekit/clear.py`); the geometry step clears them
   before `design()`.
3. `build` until `checks` passes and the renders look right; then a person reviews.

## Building README

Each building's README stays short (10-25 lines). Numbers come from the build
(`work/logs/checks.log`); no dates, history or review notes. What a faction shares (palette,
night rules) is said once in its `ROLLOUT.md` or `style.py`.

```markdown
# <Faction> <building> (`<ObjectName>`)

Model `<Model>`, mesh `<MESH>`, own texture `<Own>.tga` (from `<EA>.tga`). `Tier.<T>`.

## What changed
- **<Part>**: what was added, one line each. **Banners**: <n>, cloth in `<HCModel>`.

## Kept clear
- <door swing, unit path, neighbour joint>: the limit.

## Status
Installed | Built, not installed | Stub. <EA> -> <ours> triangles, height <a> -> <b>, <n>/<n> checks.
States left to EA, and why.

## Known limits
- What is wrong, unchecked, or left to EA.
```

## What sagekit already knows (so a recipe never has to)

- The asset cache (`asset.dat`) filing every model and texture, and how to register new ones
  (a texture without a record renders magenta; a model with a stale record renders invisible).
- What Blender's W3D exporter drops, and how to restore it (`sagekit/formats/w3d.py`).
- The game's normal-map convention (red inverted against Blender's; `sagekit/paint/imageio.py`).
- Which archive the game takes each file from, ignoring the archives this repo installs.

## Lifecycle, parts, add-ons

`inventory` lists every **part** (each Draw module of the building's objects: body, door, banner,
add-ons like the fortress's flame launchers, oil casks, statues, catapult tower) and every
**condition** it is drawn in: healthy, construction, damaged, really damaged, rubble, snow,
stonework, placement, LOD medium/low, and the **upgrades** that switch a part on
(`fortress_improvement_1`, `upgrade_fortress_monument`, ...). A building's `parts` and
`built_states` say what its recipe covers; `[x]` marks done.

The construction, really damaged and rubble models follow our body automatically. `derive`
gives the ones whose body is EA's healthy one our body as it is; `lifecycle` rebuilds the rest
along EA's pieces, cuts and animations, and one below the checks' standard stays EA's. The
build's `work/lifecycle.json` says which models were rebuilt, derived or left to EA, and why;
`renders/lifecycle/<model>.png` shows EA's model against ours. A recipe tunes a model with
`lifecycle = {"DBTower_D3": {"tolerance": 3.0}}` (`sagekit/lifecycle.py`). The steps in detail:
[docs/ART.md](../docs/ART.md).

An add-on's banners (cloth on a recipe whose `parts` show only under an upgrade flag: the Elven
anvil, the Dwarven monument) never go into the object's house model, which the game draws before
the upgrade is bought: they get a model of their own from the style's `house_template`
(`EBHCFAnvil`), whose Draw repeats the add-on Draw's condition states in order, so it shows exactly
when the add-on does and draws nothing where the add-on's model is being built or broken
(`Building.addon_conditions`). Nothing to declare in the recipe.

## Models other factions share

When the model is drawn by other factions too (the Dwarven castle walls' tower, postern and
trebuchet draw Gondor's `GBWallTwr`, `GBWallPG`, `GBWallTreb`), redesigning it in place would change
them as well. The recipe then declares `own_model = "DBWallTwr2"` (and optionally `replaces`, EA's
stand-in meshes its target takes over): the build works on a renamed copy, ships it under the new
name with its own texture, and only this faction's Draw modules are repointed to it
(`sagekit/owncopy.py`; example `dwarves/oldwall_tower`). The name must be one EA's files don't use.

The same holds for house-colour models: when another faction draws the house model a building's cloth
goes to (Arnor draws `NBHCElvnBarx` and `EBHCMalTree` beside the Elven barracks and mallorn), the
house step ships an own copy (`EBHCElvnBarx`, `EBHCMalTree2`) shown by this faction's Draw modules
only (`Building.own_house_copy`); nothing to declare in the recipe.

## Sheets other factions share

A mesh we ship untouched can still be painted from another faction's sheet: the Dwarven siege
works' anvil samples the Elven forge's `EBForge.tga` (Isengard, Mordor and the Goblins share
`WBCave`). Recolouring that sheet would change the other factions, so the faction's `style.py`
declares a copy of its own, `shared_sheets = {"EBForge.tga": "DBAnvil.tga"}` (same name length:
W3D patches names in place). The build's `shared` step renames the sheet (and its _D/_Snow
variants) in every model the building ships, recolours it like `sagekit sheets` does, ships and
registers it, and adds the copy's INI state swaps; EA's sheet and its normal map stay EA's
(`sagekit/sharedsheets.py`). One copy per faction: every building that shows the sheet uses it.

## Night lights

EA lights a building at night by showing sub-objects its INI names (`NightWindowName`). The
recipe marks its real windows and doors with `night_lights(kit)` (`Light.rect`, `Light(...,
kind="door")`, `Light.glow` for a free-hanging glow card; `night_surfaces` names EA meshes a light
may lie on). The style sets the glow, `night = NightLook("DBNight.tga", ramp=...)`. The `night`
step casts the lights onto our body and later steps rebuild EA's night meshes from them under EA's
names; `renders/night/` shows EA's night look against ours. A `base` recipe (a level mesh) has no
lights or cloth unless it sets `always_shown = True`. `sagekit/nightlights.py`.

## Troop review

The [Dwarven](dwarves/troops/README.md), [Elven](elves/troops/README.md) and
[Men of the West](men/troops/README.md) troop recipes share isolated staging, weighted skin
validation and paired equipment/motion previews. Their galleries live under
`build/assets/<faction>/troops/redesign/review.html`. Troops are staged, not installed; heroes
come later. Buildings and builders install separately. A troop install must compose the current
caches and house-colour table fresh and provide `--revert`; never copy the staged caches over a
later installation.

## Tools the pipeline needs

- Blender 4.5 with the OpenSAGE W3D add-on (`io_mesh_w3d`), at `/Applications/Blender.app`
  (or set `SAGEKIT_BLENDER`).
- ImageMagick (`magick`).
- Real-ESRGAN (ncnn-vulkan build, macOS) in `downloads/realesrgan/` (binary + `models/`), from
  github.com/xinntao/Real-ESRGAN releases: the 4x upscale of each faction's atlas.
